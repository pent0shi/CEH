1. Module at a Glance

Module 18: IoT and OT Hacking

  • IoT connects physical objects to IP networks so they can sense and share data.
  • OT monitors or changes physical industrial processes through ICS equipment.
  • IoT attacks target devices, radios, firmware, cloud services, and default credentials.
  • OT attacks target PLCs, HMIs, SCADA, industrial protocols, and trusted suppliers.
  • Defense combines asset visibility, segmentation, secure updates, and safe monitoring.

Why it matters: A compromised camera can become a botnet member. A compromised PLC can stop production or damage equipment. Confidentiality matters, but OT also depends heavily on availability, integrity, safety, and deterministic timing.

What the exam usually asks: Purdue levels, ICS component roles, protocol-to-port matches, Modbus weakness, Nmap OT scripts, Shodan filters, SDR and firmware tools, rolling-code steps, OWASP IoT items, MITRE ATT&CK for ICS tactics, and the safest countermeasure for a live plant.

Ten things to remember most:

  1. Edge -> access gateway -> internet -> middleware -> application is the IoT stack.
  2. Purdue Level 0 is the physical process; Level 3 is site operations; Level 3.5 is the industrial DMZ; Levels 4 and 5 are enterprise systems.
  3. PLC executes control logic; RTU collects remote field data; HMI displays and accepts operator commands; SCADA supervises; DCS controls a distributed plant.
  4. Modbus TCP uses port 502 and normally has no authentication or encryption.
  5. DNP3 uses 20000; EtherNet/IP uses 44818; S7 uses 102; BACnet uses UDP 47808.
  6. A rolling-code attack jams reception, captures codes, forwards one, and saves another unused valid code for later.
  7. Shodan finds exposed devices; Nmap identifies services; Nessus finds known vulnerabilities; Malcolm analyzes network traffic.
  8. UART, SPI, I2C, and JTAG are hardware interfaces. JTAG is a debug/test interface.
  9. Active scanning can crash fragile OT devices. Prefer passive discovery first.
  10. Zero trust means verify explicitly and grant least privilege, even inside OT.

3. Topic-by-Topic Guide

3.1 Learning objectives, IoT meaning, and data flow

What it is: The Internet of Things (IoT), also called the Internet of Everything (IoE) in the notes, is a network of IP-addressable objects with embedded sensors, processors, and communication hardware. A "thing" can be natural, human-made, or machine-made. The module objectives are IoT concepts, attacks, methodology and defense, followed by the same four areas for OT.

Analogy: A smart thermometer is a receptionist who reports room temperature to a head office and accepts instructions back.

How it works:

  1. Industrial, wearable, healthcare, and home devices sense or collect data.
  2. They send data, often through an IoT gateway, across the internet.
  3. Cloud storage or servers store and analyze the data.
  4. A mobile app displays results and can send a remote-control command.
  5. The gateway returns the command to the device, which changes its behavior.

Real-world use: A factory motor reports vibration. Analytics detects an unusual pattern, and an authorized maintenance application schedules inspection. If default credentials protect the gateway, an outsider could instead read or alter the data.

Tools and commands used here: No tool is needed to define the flow. Later pages use Shodan, Nmap, Wireshark, firmware tools, and radio tools against its weak points.

AI angle (ADDED CONTEXT): AI can classify sensor anomalies and summarize asset inventory. An attacker can use AI to prioritize exposed devices from public banners. Example defensive prompt: "Group these authorized asset records by protocol, owner, patch status, and internet exposure. Do not suggest active tests."

Countermeasures and defense: Know every data producer and consumer. Authenticate devices and users, encrypt transport, restrict commands, and log administrative changes.

EXAM FOCUS: IoT is not only smart homes. The key property is embedded sensing or control plus network communication. A gateway translates or connects devices; it is not the same as cloud middleware. Trap: assuming every device directly uses a full TCP/IP stack and talks directly to an app.

Memory trick: "Sense, Send, Store, Study, Steer" describes sense, transmit, store, analyze, and command.

3.2 IoT architecture, technologies, operating systems, and protocols

What it is: The five layers separate physical sensing from user applications.

Analogy: A parcel moves from a local shop, through a regional depot and roads, to a sorting warehouse, and finally to the customer.

How it works:

  1. Edge technology: sensors, devices, machines, and intelligent edge nodes.
  2. Access gateway: protocol translation and messaging between local and IP networks.
  3. Internet: connectivity between endpoints and remote services.
  4. Middleware: device management and information management.
  5. Application: delivers applications to different IoT users.

Technology groups from the notes:

  • Short range: BLE, Li-Fi, NFC, QR codes and barcodes, RFID, Thread, Wi-Fi, Wi-Fi Direct, Z-Wave, Zigbee, and ANT.
  • Medium range: HaLow and LTE-Advanced.
  • Long range: LPWAN, LoRaWAN, 6LoWPAN, Sigfox, Neul, VSAT, cellular, and NB-IoT.
  • Wired: Ethernet, MoCA, and power-line communication (PLC), which is unrelated to a programmable logic controller with the same abbreviation.
  • Operating systems: Windows 10 IoT, Amazon FreeRTOS, Fuchsia, RIOT, Ubuntu Core, ARM Mbed OS, Zephyr, Embedded Linux, NuttX RTOS, Integrity RTOS, and Tizen.
  • Application protocols: CoAP, Edge, LWM2M, Physical Web, XMPP, Mihini/M3DA, and MQTT.

Real-world use: A battery soil sensor can use Zigbee to a gateway. The gateway uses IP networking to reach middleware, where MQTT messages become application data.

Tools and commands used here: Wireshark can decode MQTT and Zigbee. Open Sniffer, CatSniffer, and KillerBee examine low-power wireless traffic.

ADDED CONTEXT: MQTT is lightweight publish/subscribe messaging through a broker. CoAP is a REST-like protocol for constrained devices. LWM2M adds device management. XMPP is extensible XML messaging. 6LoWPAN adapts IPv6 to IEEE 802.15.4 links; it is not simply a long-range radio like LoRaWAN.

AI angle (ADDED CONTEXT): A model can explain a decoded protocol or flag an unexpected topic. Example prompt: "Explain this authorized MQTT packet capture field by field and identify plaintext metadata without inventing payload contents."

Countermeasures and defense: Authenticate the gateway and broker, restrict topics, encrypt where supported, and remove unused radio and management services.

EXAM FOCUS: Match the function to the layer. Protocol translation means access gateway; device management means middleware; sensors mean edge. Trap: placing MQTT at the physical layer. It is an application protocol, normally carried over TCP.

Memory trick: "Every Access Internet Message Arrives": Edge, Access, Internet, Middleware, Application.

3.3 OWASP IoT Top 10, attack surfaces, and device vulnerabilities

What it is: OWASP lists recurring weaknesses, not a sequence of attacks.

Analogy: A building risk register lists unlocked doors, copied keys, old cameras, and unguarded loading bays before describing individual burglaries.

OWASP Top 10 IoT threats in notes order:

  1. Weak, guessable, or hardcoded passwords.
  2. Insecure network services.
  3. Insecure ecosystem interfaces.
  4. Lack of secure update mechanisms.
  5. Use of insecure or outdated components.
  6. Insufficient privacy protection.
  7. Insecure data transfer and storage.
  8. Lack of device management.
  9. Insecure default settings.
  10. Lack of physical hardening.

Eighteen attack surfaces: ecosystem, device memory, physical interfaces, web interface, firmware, network services, administrative interface, local storage, cloud web interface, third-party backend APIs, update mechanism, mobile application, vendor backend APIs, ecosystem communication, network traffic, authentication/authorization, privacy, and hardware sensors.

The seventeen vulnerability lessons:

  • Username enumeration reveals valid names through different authentication responses.
  • Weak passwords such as 1234 and unchanged factory passwords permit guessing.
  • No lockout after three to five failures permits continued guessing.
  • Unencrypted services expose traffic; weak implementations such as SSLv2 are not adequate merely because encryption is present.
  • Missing two-factor authentication leaves one stolen secret sufficient.
  • Updates without TLS or file encryption, and world-writable update storage, allow tampering. No manual check or no update mechanism leaves flaws unresolved.
  • Denial of service can disable one service or the entire device.
  • Removable storage and firmware extraction can reveal source, binaries, passwords, and SSH keys. Hidden firmware version and update date hinder risk decisions.
  • JTAG with a debugger can alter execution; side channels can leak or change behavior.
  • Serial console access can yield a full shell even when boot protections exist.
  • Outdated BusyBox, OpenSSL, SSH, or web server components carry known weaknesses.

Real-world use: An authorized reviewer extracts a camera firmware image, finds a hardcoded credential, and reports it before the same credential is used at scale.

Tools and commands used here: Binwalk, Firmware Mod Kit, strings, hexdump, GDB, OpenOCD, BUS Auditor, Shodan, and Nmap appear in later topics.

AI angle (ADDED CONTEXT): AI can map findings to OWASP categories, but evidence must support each mapping. Prompt: "Classify these verified findings under the OWASP IoT Top 10 and quote the supporting observation for each."

Countermeasures and defense: Unique credentials, lockout, MFA, signed updates, component inventory, data minimization, encrypted storage, lifecycle management, secure defaults, disabled debug ports, and tamper resistance address the list.

EXAM FOCUS: An insecure mobile app, cloud API, or backend belongs to the IoT ecosystem too. Trap: choosing only the physical device. Hardcoded password is a credential flaw; outdated OpenSSL is an insecure/outdated component.

Memory trick: For the Top 10, group them as "Secrets, Services, Surrounding interfaces, Software updates and Supply components; Privacy, Protection of data, Provisioning, Presets, Physical access."

3.4 IoT threat catalogue, DDoS botnets, and HVAC pivoting

What it is: The notes list 21 threats: DDoS, HVAC attack, rolling code, BlueBorne, jamming, backdoor remote access, Telnet remote access, Sybil, exploit kits, MITM, replay, forged malicious device, side channel, ransomware, client impersonation, SQL injection, SDR-based attack, fault injection, network pivoting, DNS rebinding, and firmware-over-the-air (FOTA) update attack.

Analogy: A botnet is a crowd of compromised smart devices all knocking on one door at the attacker's signal.

How an IoT DDoS works:

  1. The attacker exploits device weaknesses and installs malicious software.
  2. Remote access turns many devices into bots, collectively an army of botnets.
  3. A command-and-control (C2 or C&C) center sends instructions.
  4. Distributed bots send a large request volume to the target.
  5. The server exhausts resources, goes offline, or cannot process further requests.

HVAC attack steps:

  1. Shodan identifies an exposed, vulnerable industrial control or HVAC system.
  2. Default credentials provide access to the ICS/HVAC interface.
  3. The attacker changes temperature or uses the trusted connection to enter the LAN.
  4. The compromised building system becomes a network-pivoting foothold.

Real-world use: An assessor finds that a facilities network can reach finance. The safest result is a segmentation finding, not an attempt to alter temperature.

Tools and commands used here: Shodan, Censys, Nmap, botnet malware, and the iRidium interface shown in the HVAC example.

AI angle (ADDED CONTEXT): Attackers can generate convincing phishing content for initial compromise. Defenders can cluster traffic to identify bot-like behavior. Prompt: "Summarize common timing and destination features in this authorized flow export and list benign explanations."

Countermeasures and defense: Remove internet exposure, change credentials, patch, segment facilities networks, rate-limit, filter egress, and prepare DDoS absorption with the ISP or upstream provider.

EXAM FOCUS: C2 coordinates bots; the target server is the victim of the flood. HVAC is often the initial access or pivot, not the final target. Trap: calling every large infection a DDoS before a flood is launched.

Memory trick: DDoS chain is "Break in, Bot, Beacon, Blast, Blackout."

3.5 Rolling-code and jamming attacks

What it is: A rolling code, or hopping code, changes on each key-fob use to stop simple reuse. The described attack combines jamming, capture, and selective replay. Jamming means transmitting interference on the same frequency so endpoints cannot reliably send or receive messages.

Analogy: An attacker blocks a mailbox, collects two signed entry slips, hands over the first to avoid suspicion, and keeps the second unused slip.

How the rolling-code attack works:

  1. The victim presses the fob. The attacker jams the car receiver and sniffs code one.
  2. The car does not unlock, so the victim presses again.
  3. The attacker captures code two and forwards code one, which unlocks the car.
  4. Code two remains unused and valid in the receiver's expected sequence.
  5. The attacker later replays code two to unlock the vehicle.

How jamming works: The attacker determines the sensor frequency, transmits random radio energy there, and reduces the signal-to-noise ratio until communication fails.

Real-world use: A vehicle-security team tests a owned fleet receiver in a shielded environment and confirms that request failure plus a second press is a warning sign.

Tools and commands used here: RFCrack, YardStick One, HackRF One, RTL-SDR, RFCrack.py -j, and RFCrack.py -r with modulation and frequency options.

Countermeasures and defense: Use authenticated, freshness-protected protocols, receiver-side anomaly detection, rolling-window limits, and user warnings after repeated failed unlocks. Encryption alone does not prevent radio jamming.

EXAM FOCUS: The second code is saved; the first code is forwarded to preserve normal behavior. Trap: a basic replay resends an old message, while this scenario specifically needs jamming plus capture of an unused future code.

Memory trick: "Jam one, Grab one; Jam two, Grab two; Send one, Save two."

3.6 Backdoors, Telnet, BlueBorne, and smart-grid compromise

What it is: A backdoor is hidden or unauthorized access that bypasses normal authentication. Telnet is an old remote terminal protocol whose normal traffic, including credentials, is plaintext. BlueBorne is a family of Bluetooth attacks; the notes associate it with airborne replay, fuzzing, and jamming using SDR hardware.

Analogy: A phishing attachment is a fake delivery worker who quietly installs a spare key inside the building.

How the smart-grid example works:

  1. The attacker profiles employees using social engineering.
  2. A legitimate-looking phishing email carries a malicious attachment.
  3. Opening it installs a backdoor and gives access to the private network.
  4. The attacker pivots to SCADA and disables a UPS or other power controls.
  5. Loss of power causes operational impact.

How Telnet access works: Scanning or Shodan reveals TCP 23. Weak/default login details or an unprotected service then provide a remote command session. The example also shows a Dahua DVR and HTTP port 80, so an open web port is not itself Telnet.

Real-world use: A utility removes direct Telnet, requires a VPN and jump host, and trains staff to report attachments instead of testing them on production systems.

Tools and commands used here: Shodan, Censys, Nmap, HackRF One, and Telnet.

AI angle (ADDED CONTEXT): Generative AI can make phishing grammatically convincing and deepfake voice can support impersonation. Defenders should verify unusual requests through a second channel. Prompt for awareness work: "List benign warning signs in this fictional email without improving its persuasive content."

Countermeasures and defense: Use SSH rather than Telnet, email filtering, attachment sandboxing, MFA, least privilege, Bluetooth patching, and restricted device discovery.

EXAM FOCUS: SSH is the secure Telnet replacement. BlueBorne is Bluetooth, not Wi-Fi. Trap: choosing a firewall as the complete answer to phishing; user reporting and endpoint/email controls address the initial attachment.

Memory trick: "Telnet Talks in Text"; "BlueBorne Bites Bluetooth."

3.7 SDR attacks, local discovery, and DNS rebinding

What it is: Software-defined radio (SDR) implements radio functions in software. It can inspect, modify, generate, or replay signals. DNS rebinding makes a browser resolve one hostname first to an attacker and then to a private address, helping malicious script reach local devices through the victim browser.

Analogy: SDR is a programmable musical instrument that can learn and replay many songs. DNS rebinding is a signpost that is changed after a visitor passes the gate.

Three SDR methods in the notes:

  1. Replay: discover the frequency, capture an original command, isolate the command sequence, and inject it back into the IoT network.
  2. Cryptanalysis: capture and reverse-engineer the signal/protocol, requiring knowledge of cryptography, communication theory, and modulation.
  3. Reconnaissance: inspect specifications and hardware; a multimeter and chipset inspection can identify ground pins, product IDs, and other information.

Local device discovery steps:

  1. A user visits an attacker-controlled advertisement or page.
  2. Malicious code obtains the local IP and probes available private addresses.
  3. Active devices may return TCP RST; inactive ones may time out.
  4. Responses reveal devices and potentially access-point UID and BSSID information.
  5. A tool such as Singularity of Origin tests DNS rebinding.
  6. Successful rebinding lets the page interact with local device interfaces.

Real-world use: A browser-security assessment uses a dedicated test network to show why an unauthenticated local camera interface is reachable from a web page.

Tools and commands used here: HackRF One, RTL-SDR, RFCrack, Singularity of Origin, Wireshark, and TCP SYN/RST responses.

Countermeasures and defense: Authenticate local interfaces, validate Host headers, use DNS rebinding protections, isolate IoT networks, and require explicit user approval for local network access where the platform supports it.

EXAM FOCUS: RST can reveal a closed port on a live host; timeout gives less certain evidence. BSSID identifies a wireless access point radio. Trap: calling rebinding ordinary DNS spoofing; rebinding abuses changing answers and browser trust.

Memory trick: SDR does "Record, Reverse, Recon"; rebinding does "Answer, Alter, Access."

3.8 Fault injection and the remaining IoT attack types

What it is: Fault injection, also called perturbation, deliberately disturbs hardware so it skips checks, leaks data, or executes unintended behavior. It can be invasive, which alters or opens the package, or non-invasive, which works externally.

Analogy: A momentary flicker can make a cashier skip a verification step.

Fault methods and other attacks:

  • Optical, electromagnetic fault injection (EMFI), and body-bias injection (BBI) use lasers, electromagnetic pulses, or bias changes.
  • Power, clock, and reset glitching disturb supply or timing.
  • Voltage/frequency tampering changes operating conditions; temperature attacks alter the chip environment.
  • Sybil uses multiple forged identities, for example to simulate traffic congestion.
  • Exploit kits automate scripts against poorly patched vulnerabilities.
  • MITM secretly intercepts and can modify two-party communication.
  • Replay resends captured valid messages, potentially causing repeated actions or DoS.
  • Forged malicious device replacement needs physical or supply-chain access.
  • Side channel derives secrets from emissions or behavior rather than breaking math.
  • Ransomware locks a screen or encrypts files to deny access until payment is demanded.
  • Client impersonation pretends to be a legitimate client; SQL injection inserts database commands through unsafe input; FOTA attacks abuse firmware updates.

Real-world use: A hardware lab tests whether a voltage glitch bypasses secure boot on a development board, then adds brownout detection and boot verification.

Tools and commands used here: Oscilloscope, signal analyzer, multimeter, glitching equipment, and debug interfaces.

Countermeasures and defense: Use secure boot, signed firmware, glitch sensors, constant-time authentication, tamper evidence, nonces and timestamps for anti-replay, input validation, parameterized SQL, and offline backups.

EXAM FOCUS: Fault injection changes execution conditions; side channel observes behavior. Sybil means many identities; MITM means an intermediary. Trap: selecting encryption as an anti-jamming control or a replay defense without freshness.

Memory trick: "Light, Magnet, Bias; Power, Clock, Reset; Volt, Hertz, Heat."

3.9 IoT malware and botnet families

What it is: IoT malware turns weakly protected devices into botnet members, proxies, miners, ransomware victims, or attack platforms.

Analogy: One unchanged factory key can open thousands of houses of the same model.

How it works: KmsdBot's Kmsdx variant adds Telnet scanning/authentication, targets SSH exposure and default credentials, and supports more CPU architectures. The notes' Go-source analysis mentions redress, main.go, ssh.go, telnet.go, and a telnet.txt credential list. These are static-analysis clues, not commands to run. Other listed families are WailingCrab, P2PInfect, NKAbuse, IoTroop, and XorDdos.

ADDED CONTEXT: IoTroop is also known as Reaper. XorDdos targets Linux systems. P2PInfect uses peer-to-peer propagation and has targeted Redis. NKAbuse uses NKN networking for decentralized communication. WailingCrab has used MQTT for C2. Family capabilities change, so answer from the behavior described in the question.

Real-world use: A defender finds repeated outbound Telnet attempts from a camera. The response is isolation, credential replacement, firmware remediation, and checking peer devices rather than merely deleting one suspicious process.

Tools and commands used here: Redress for Go binary inspection, Shodan, Censys, network monitoring, and anti-malware tools.

AI angle (ADDED CONTEXT): AI can help label static functions but may hallucinate malware capabilities. Prompt: "Describe only observable behavior in these decompiled snippets and mark uncertain claims; do not generate propagation code."

Countermeasures and defense: Unique credentials, disable Telnet, restrict egress, patch firmware, monitor unusual scanning, and rebuild compromised devices from trusted images.

EXAM FOCUS: Default credentials plus broad architecture support increase botnet reach. Trap: treating Telnet scanning as exploitation of SSH; they are different services even when one malware family targets both.

Memory trick: "Scan, Sign in, Spread, Serve C2."

3.10 Information gathering with Shodan and wireless sniffing

What it is: Information gathering identifies exposed devices and their protocols before vulnerability validation. Shodan indexes internet-facing services; sniffing observes traffic within range or on a monitored network.

Analogy: Shodan is a searchable directory of public shop signs; sniffing is listening to conversations on a network you are authorized to monitor.

How it works:

  1. Query Shodan for webcamxp country:"US", webcamxp city:"paris", or webcamxp geo:"-50.81,201.80" as shown in the notes.
  2. Review IP, hostname, ISP, location, ports, and service banners without assuming that a banner proves exploitability.
  3. Scan authorized ranges for HTTP ports 80, 81, 8080, and 8081.
  4. Identify the wireless adapter with ifconfig, enable monitor mode, discover the target channel, then capture that channel in Wireshark.
  5. The notes' capture shows MQTT Ping Request/Response and Publish exchanges, with destination TCP 1883.

Real-world use: An asset owner confirms that no camera is internet exposed and uses an approved wireless capture to identify plaintext telemetry.

Tools and commands used here: Shodan, MultiPing, FCC ID Search, Censys, FOFA, Nmap, ifconfig, Airmon-ng, Airodump-ng, Wireshark, Suphacap, and IoT sniffing tools.

AI angle (ADDED CONTEXT): ChatGPT or ShellGPT can explain a command before an approved scan. Prompt: "Explain each Nmap flag in this authorized HTTP discovery command and warn which options increase traffic." Never paste private scope or credentials into a public model.

Countermeasures and defense: Remove public administration interfaces, change identifying banners where practical, encrypt MQTT with TLS, use broker ACLs, and monitor for unexpected monitor-mode or scanning activity.

EXAM FOCUS: Shodan is search, not an exploit framework. Monitor mode captures wireless frames; the channel must match. Trap: airodump-ng scans/captures while airmon-ng configures monitor mode.

Memory trick: "Shodan Sees, Nmap Scans, Wireshark Watches."

3.11 IoT vulnerability scanning and validation

What it is: Vulnerability scanning checks discovered devices for default credentials, known weaknesses, product paths, and versions.

Analogy: A safety inspector checks each lock model against a recall list instead of forcing every door.

How it works: IoTSeeker's Perl scanner accepts IP addresses and reports device type and whether the default password remains. Genzai identifies routers, cameras, and HMIs, then tests default passwords and vulnerabilities based on paths and versions. Its example mentions a TP-Link router result. Other listed tools are beSTORM, IoTSploit, IoTVAS, and Firmalyzer.

Real-world use: A hospital runs an approved credentialed scan against decommissioned test cameras and prioritizes any device still using factory credentials.

Tools and commands used here: IoTSeeker/IotScanner.pl, Genzai, beSTORM, IoTSploit, IoTVAS, Firmalyzer, and Nmap.

Countermeasures and defense: Use an asset inventory, authenticated configuration review, vendor advisories, firmware updates, and manual validation of high-risk results. Avoid password attempts or intrusive scans outside authorization and maintenance windows.

EXAM FOCUS: Discovery finds devices; vulnerability scanning maps them to known weaknesses; exploitation proves impact. Trap: treating "changed password" as proof that the password is strong or the device is fully patched.

Memory trick: "Seeker Seeks Secrets; Genzai Gathers Versions."

3.12 RFCrack, Open Sniffer, and HackRF One

What it is: These are radio test tools. RFCrack works with YardStick One for sub-GHz tests. Open Sniffer captures IEEE 802.15.4/Zigbee frames into Wireshark and can transmit frames. HackRF One is a half-duplex SDR covering about 1 MHz to 6 GHz.

Analogy: They are universal radio microscopes, with some models also able to speak.

How it works:

  1. RFCrack live replay uses -i; rolling-code mode uses -r with -M MOD_2FSK and a frequency such as -F 314350000; -U -100 -L -10 sets RSSI bounds; -j -F 314000000 selects jamming.
  2. Open Sniffer captures Zigbee beacon and command frames, permits visualization, supports user-defined replay, and can continuously emit packets for DoS testing.
  3. HackRF supports receive and transmit, but not simultaneously in full duplex. It can inspect protocols from GSM to Z-Wave and support replay, fuzzing, or jamming.

Real-world use: A lab uses RFCrack on a owned sub-GHz gate controller and Open Sniffer on an isolated Zigbee network to verify replay resistance.

Tools and commands used here: RFCrack.py, YardStick One, Open Sniffer, Wireshark, HackRF One, KillerBee, and CatSniffer.

Countermeasures and defense: Use cryptographic authentication and freshness, monitor spectrum anomalies, reduce radio range where possible, and test only in a controlled RF environment.

EXAM FOCUS: MOD_2FSK is modulation, frequency is in Hz, RSSI bounds select signal strength, and half duplex means one direction at a time. Trap: selecting Wireshark as the radio transmitter; it primarily decodes and analyzes captures.

Memory trick: "I is Immediate replay, R is Rolling, J is Jamming, F is Frequency."

3.13 HackRF replay and hardware communication buses

What it is: A replay capture stores radio samples and transmits them again. Hardware buses expose internal communications and debugging functions.

Analogy: A sample file is an audio recording of a radio conversation. UART, SPI, I2C, and JTAG are different service hatches on the circuit board.

How it works:

  1. FCC ID records or an RTL-SDR help identify a target transmitter's frequency.
  2. hackrf_transfer -r receives raw samples; -t transmits a capture; -f sets frequency, and gain options control receive or transmit amplification.
  3. hackrf_info confirms board identity and firmware version.
  4. BUS Auditor scans pin combinations and voltage settings for UART or I2C.
  5. UART output can reveal RX/TX pins and baud rate such as 9600; I2C output reveals device address plus SCL clock and SDA data pins.

Interface meanings: UART is asynchronous serial communication. SPI is synchronous serial communication with a controller and peripherals. I2C is addressed two-wire communication. JTAG is a test/debug interface useful for firmware and execution access. DIVA is a training application, and a PCB is the physical circuit board inspected.

Real-world use: A product team locates an enabled debug UART on a prototype, observes boot logs, and disables sensitive console access before release.

Tools and commands used here: HackRF One, RTL-SDR, BUS Auditor, DIVA, multimeter, GDB, and OpenOCD.

Countermeasures and defense: Lock or disable debug interfaces in production, require authenticated debug unlock, use tamper detection, and never rely on hidden test points as a security boundary.

EXAM FOCUS: UART commonly leads to a console; JTAG commonly leads to debugging; I2C uses SCL and SDA. Trap: confusing a baud rate with radio frequency.

Memory trick: "UART Usually A Root Terminal; JTAG Joins Test And Debug Gates."

3.14 NAND glitching, CamOver, and Telnet access

What it is: NAND glitching interrupts boot by grounding a serial I/O pin of flash memory, with the goal of bypassing normal startup and gaining root. CamOver targets certain network-camera password-disclosure weaknesses.

Analogy: NAND glitching distracts a guard during the first seconds of a shift. CamOver uses a known defective desk procedure to ask for the administrator key.

How it works:

  1. For NAND glitching, identify the flash and timing, disturb serial I/O during boot, and inspect whether a privileged console appears. Results are hardware dependent.
  2. Start CamOver with camover; choose one address with -a, input files with -i, output with -o, threads with -t, or internet results through Shodan/ZoomEye.
  3. For Telnet, identify open TCP 23 and use only authorized credentials. Shodan or Censys may expose a device banner before any login attempt.

Real-world use: An authorized camera audit verifies whether a patched firmware release removes password disclosure and whether Telnet is fully disabled.

Tools and commands used here: CamOver, Shodan, ZoomEye, Censys, Nmap, Telnet, multimeter, and hardware-glitching tools.

Countermeasures and defense: Patch camera firmware, restrict management networks, replace Telnet with SSH, require strong unique credentials, and add boot/flash glitch detection.

EXAM FOCUS: CamOver is a camera exploitation tool, not a generic camera search engine. -a is one address; -t means threads in its usage, not target. Trap: trying Shodan API access without a key when a local -a test is intended.

Memory trick: "Camera Address = CamOver -a; Telnet Twenty-Three = Text."

3.15 Maintaining access through firmware modification

What it is: Firmware is the low-level software that runs a device. An attacker who modifies and reinstalls it can persist across ordinary account changes.

Analogy: Instead of keeping a copied house key, the intruder replaces the lock's internal instructions so it always admits them.

How it works:

  1. After authorized access in an assessment, obtain the firmware image.
  2. Firmware Mod Kit's extract-firmware.sh identifies and extracts components.
  3. The DD-WRT example shows a TRX header, gzip/LZMA compressed data, and a Squashfs filesystem, plus a checksum and offsets.
  4. Modify files only in an owned lab image, reconstruct it, and verify whether the device accepts unsigned or improperly validated firmware.
  5. The security finding is an update-verification failure with persistence impact.

Real-world use: A vendor test shows that a modified image is rejected because secure boot checks a trusted signature. This proves the control, not an attack success.

Tools and commands used here: Firmware Mod Kit, Binwalk, dd, file, strings, hexdump, mount, GDB, and QEMU.

Countermeasures and defense: Require signed images, verify a hardware root of trust, use rollback protection, protect update storage, and reflash compromised devices from known-good media.

EXAM FOCUS: Firmware modification is maintaining access, not initial access. Squashfs is a compressed filesystem; TRX is a router firmware image format. Trap: assuming password removal deletes implanted firmware.

Memory trick: "Extract, Examine, Edit, Encode, Evaluate."

3.16 Firmware analysis and reverse engineering

What it is: Static analysis inspects an image without running it. Dynamic analysis observes emulated or real execution. Reverse engineering reconstructs behavior.

Analogy: Static analysis opens and catalogs a machine; dynamic analysis runs it behind safety glass.

How it works:

  1. Obtain firmware from the device or vendor and verify the MD5 value as an integrity comparison, not as collision-resistant security.
  2. Run file, strings, and hexdump on the .bin; use Binwalk to identify and extract embedded data, and dd for precise byte ranges.
  3. Create rootfs, mount the extracted filesystem when appropriate, and inspect etc/passwd, etc/shadow, and etc/ssl.
  4. Search recursively for password, admin, root, .conf, .pem, and .crt data.
  5. Emulate binaries with qemu-mipsel, qemu-arm, or the matching QEMU architecture and -L library prefix. Test the web interface dynamically.

Goals from the notes: passwords, API tokens, endpoints, vulnerable services, backdoor accounts, configuration files, private keys, and stored data.

Real-world use: An assessor recovers an API token from a vendor-supplied image and proves exposure without touching production cameras.

Tools and commands used here: File, MD5 tools, strings, hexdump, Binwalk, dd, mount, grep, find, QEMU, GDB, Radare2, Ghidra, and IDA Pro.

AI angle (ADDED CONTEXT): AI can suggest likely meanings for strings or decompiled functions. Prompt: "Summarize evidence in this firmware string listing and distinguish hardcoded secrets from harmless words containing 'key'."

Countermeasures and defense: Strip secrets, use per-device credentials, protect keys in secure hardware, remove debug artifacts, sign firmware, and manage third-party components.

EXAM FOCUS: Binwalk extracts; QEMU emulates; strings finds printable sequences; grep searches content; find searches names. Trap: choosing QEMU for static extraction or Binwalk for full processor emulation.

Memory trick: "Get, Verify, View, Unpack, Mount, Mine, Mimic."

3.18 IoT countermeasures, manufacturer guidance, and hardware practice

What it is: Defense covers accounts, network exposure, updates, physical access, and operational lifecycle.

  2. Lock accounts after excessive invalid logins.
  3. Use strong authentication.

  5. Deploy IDS/IPS.

3.19 OT, ICS components, and IT/OT convergence

What it is: Operational technology (OT) is hardware and software that detects or causes change in industrial operations by monitoring or controlling physical devices. An industrial control system (ICS) is the collection of systems, networks, devices, and controls that automate industrial processes.

Analogy: IT manages information; OT manages the movement and condition of the physical world.

Components:

  • PLC: programmable logic controller executing local deterministic control logic.
  • RTU: remote terminal unit collecting field data and issuing control at remote sites.
  • SCADA: supervisory control and data acquisition across geographically distributed processes.
  • DCS: distributed control system coordinating controllers within a plant/process.
  • HMI: human-machine interface for display and operator commands.
  • BPCS: basic process control system; SIS: safety instrumented system for safe states.
  • IED: intelligent electronic device; VFD: variable-frequency drive for motor speed.
  • PID: proportional-integral-derivative control used to hold a process at a setpoint.

IT/OT convergence and IIoT: Integration links OT monitoring/control with IT storage and processing such as SQL, Java, and Python to improve security, quality, efficiency, and productivity. Industry 4.0 uses these ideas for smart manufacturing. IIoT is IoT applied to industrial operations, supply chains, manufacturing, and management.

Real-world use: A plant historian sends carefully brokered production data to IT analytics without allowing the analytics server to directly write to a safety PLC.

Tools and commands used here: Malcolm, Wireshark, Nmap OT scripts, Nessus, Skybox, and Microsoft Defender for IoT support later assessments.

AI angle (ADDED CONTEXT): Predictive maintenance models can detect failing motors. Poisoned sensor training data could hide failure. Prompt: "Identify data-quality checks for this maintenance dataset and do not recommend changes to live control setpoints."

Countermeasures and defense: Keep safety functions independent, broker IT/OT data through controlled zones, and design for availability and safe failure.

EXAM FOCUS: HMI is the operator window; PLC is local logic; SCADA supervises wide-area operations; DCS distributes plant control. Trap: treating SIS as an ordinary business availability system instead of a safety system.

Memory trick: "PLC Performs, RTU Reaches, SCADA Supervises, DCS Distributes, HMI Helps Humans."

3.20 Purdue model and OT protocol placement

What it is: The Purdue Enterprise Reference Architecture (PERA) inspired a model of ICS zones and dependencies. The enterprise zone and manufacturing zone are separated by an industrial DMZ (IDMZ).

Analogy: A factory has public offices, a controlled reception, operations rooms, supervisor desks, machine controllers, and the machines themselves.

Levels:

  1. Level 5: enterprise network.
  2. Level 4: business logistics systems.
  3. Level 3.5: IDMZ, the brokered boundary between IT and OT.
  4. Level 3: operations systems/site operations.
  5. Level 2: control systems/area supervisory control.
  6. Level 1: basic control/intelligent devices.
  7. Level 0: physical process, sensors, and actuators.

Protocol mapping from the notes:

  • Levels 4/5: DCOM, FTP/SFTP, GE-SRTP, IPv4/IPv6, OPC UA, TCP/IP, Wi-Fi, SMTP, HTTP/HTTPS.
  • Level 3: CC-Link, GE-SRTP, HSCP, ICCP (IEC 60870-6), IEC 61850, IEC 60870-5-104, ISA/IEC 62443, Modbus, NTP, Profinet, SuiteLink, Tase.2, TCP/IP, ControlNet, Profibus PA/DP.
  • Level 2: 6LoWPAN, CC-Link, DNP3, DNS/DNSSEC, FTE, HART-IP, IEC 60870-5-101/104, IPv4/IPv6, ISA/IEC 62443, OPC, NTP, SOAP, TCP/IP, DeviceNet, AS-Interface.
  • Levels 0/1: BACnet, EtherCAT, CANopen, Crimson v3, GE-SRTP, Zigbee, ISA/IEC 62443, ISA SP100, MELSEC-Q, Modbus, Niagara Fox, Omron FINS, PCWorx, Profibus, Profinet, Sercos II, S7 Communications, WiMAX, and FOUNDATION Fieldbus.

ADDED CONTEXT: ISA/IEC 62443 is a security standard series, not a wire protocol. Protocols can appear at multiple levels depending on architecture. Learn the slide's representative placement, not an absolute rule that a protocol can exist at one level.

Real-world use: A design team places a patch broker and historian replica in the IDMZ rather than connecting the enterprise directly to Level 1 controllers.

Tools and commands used here: Firewalls, data diodes where suitable, protocol-aware monitoring, Malcolm, and securely configured jump hosts.

Countermeasures and defense: Define zones by function and risk, permit only required conduit traffic, and block direct enterprise-to-controller access.

EXAM FOCUS: Level 0 is physical process, not basic controller; Level 3.5 is IDMZ. Trap: placing business email at Level 2 or a PLC at Level 4.

Memory trick: "Five Enterprise, Four Business, Three Operations, Two Supervise, One Control, Zero Physical."

3.21 OT challenges and vulnerabilities

What it is: OT risk comes from old technology and from connections added faster than governance and protection.

Analogy: A historic machine newly connected to the internet has modern exposure but may still have decades-old locks.

The 22 challenges in notes order: lack of visibility; haphazard modernization; vulnerable communication protocols; plain-text passwords; network complexity; legacy technology; lack of antivirus; lack of skilled security professionals; rapid change; outdated systems; insecure connections; rogue devices; IT convergence; organizational challenges; unique production networks/proprietary software; remote management protocols; insufficient segmentation; physical security; vendor dependencies; resource constraints; lack of encryption; and data-integrity issues.

The ten vulnerability lessons: Publicly accessible OT permits brute force or disruption. Insecure jump boxes expose remote access. Missing updates leave known flaws. Default/weak credentials open management interfaces. Poor firewall rules spread threats. Compromised IT can reach OT placed in the corporate network, and insecure OT can also expose IT. Flat networks allow one compromise to expose all. Wireless without strong encryption/authentication permits sniffing and bypass. Unrestricted outbound OT internet access enables malware and C2.

Real-world use: A risk review finds a vendor jump host with shared credentials and direct controller access. The best fix is layered managed remote access, not just changing the shared password once.

Tools and commands used here: Asset inventory, passive monitoring, firewall/ACL review, vulnerability assessment, and identity management.

Countermeasures and defense: Compensating controls matter when patching is not immediately possible: isolation, allowlisting, virtual patching through IPS, managed access, and tested backups.

EXAM FOCUS: A flat network has insufficient segmentation. Outbound C2 needs egress restriction, not only inbound firewalling. Trap: choosing immediate patching without testing when the question stresses a fragile continuous process.

Memory trick: "Old, Open, Overconnected, Unowned, Unpatched, Unobserved."

3.22 MITRE ATT&CK for ICS

What it is: MITRE ATT&CK for ICS is a knowledge base of adversary tactics, the operational goals, and techniques, the ways those goals are achieved.

Analogy: Tactics are chapters in an intruder's plan; techniques are the specific moves used in each chapter.

Tactics and examples from the notes:

  1. Initial access: drive-by compromise, public application or remote-service exploit.
  2. Execution: change operating mode, CLI, or execution through APIs.
  3. Persistence: program modification, module firmware, APIs, project-file infection.
  4. Privilege escalation: software exploitation and hooking.
  5. Evasion: remove indicators, rootkits, or change operator mode.
  6. Discovery: network enumeration, sniffing, and remote-system identification.
  7. Lateral movement: default credentials, program download, and remote services.
  8. Collection: automated collection, information repositories, and I/O images.
  9. Command and control: common ports, connection proxy, standard application protocol.
  10. Inhibit response function: firmware update mode or block command/report messages.
  11. Impair process control: I/O brute force, parameter alteration, module firmware.
  12. Impact: property damage, loss of availability, and denial of control.

Real-world use: A SOC maps a blocked reporting message to inhibit response function and checks whether safety alarms still reach operators.

Tools and commands used here: ATT&CK Navigator, logs, network detection, asset inventory, and incident-response procedures.

AI angle (ADDED CONTEXT): AI can propose ATT&CK mappings from observed events. Prompt: "Map these verified ICS events to tactics, cite the event text, and distinguish inhibit response function from impair process control."

Countermeasures and defense: Use behavior-based detections across several tactics, independent safety protections, immutable logs, and rehearsed manual operations.

EXAM FOCUS: Blocking alarms inhibits response; changing process parameters impairs control; damage or denial of control is impact. Trap: treating discovery as initial access when the attacker is already inside.

Memory trick: "Inside Everyone Plants Persistent Evidence; Discovery Leads Collection; Control Interrupts Processes Immediately."

3.23 OT threats, HMI attacks, and side channels

What it is: The OT threat list is maintenance/administrative threats, data leakage, protocol abuse, destruction of ICS resources, reconnaissance, DoS, HMI attacks, enterprise-system/tool exploitation, spear phishing, malware, unpatched vulnerabilities, side channels, buffer overflows, and RF remote-controller abuse.

Analogy: The HMI is the plant's control-room dashboard. Compromising it can hide the real road and send wrong driving instructions.

How HMI compromise works: Attackers target the central visualization/control hub to damage SCADA devices or steal architecture information. Memory corruption includes out-of-bounds read/write and heap/stack buffer overflow. Credential weaknesses include hardcoded and cleartext passwords. Cleartext data, insecure defaults, weak authentication/authorization, unsafe ActiveX controls, missing encryption, and code injection enable further compromise.

Side-channel methods: Timing analysis compares authentication time to infer correct password characters. Power analysis uses an oscilloscope/measuring probe and analysis software to compare power consumption across clock cycles and infer character values.

Real-world use: A vendor removes hardcoded HMI credentials and tests patched runtime software against malformed project files before plant deployment.

Tools and commands used here: Debuggers, fuzzers, oscilloscopes, signal analyzers, and HMI/SCADA vulnerability scanners.

Countermeasures and defense: Patch HMI software, remove ActiveX dependence, use memory-safe development and input validation, unique credentials, MFA at access boundaries, constant-time authentication, and power/timing leakage resistance.

EXAM FOCUS: Buffer overflow is memory corruption; cleartext credential storage is credential management. Trap: choosing network sniffing when the evidence is oscilloscope power traces.

Memory trick: "HMI Holds Manipulation and Information"; "Time Tells, Power Paints."

3.24 PLC rootkits, Evil PLC, RF controllers, and supply chains

What it is: A PLC rootkit hides in controller execution and manipulates I/O. An Evil PLC attack weaponizes a PLC against engineering workstations. Industrial RF attacks abuse remote-control transmitters. Supply-chain attacks arrive through trusted hardware, software, services, or relationships.

Analogy: A rootkit changes the machine's reflexes. Evil PLC turns the machine into a trap for its mechanic. Re-pairing replaces the machine's recognized remote.

PLC rootkit sequence:

  1. Discover an exposed PLC with Shodan or obtain access through default credentials.
  2. Gain root/control-flow access and map the physical process plus I/O-pin/logic links.
  3. Modify I/O initialization, debug registers, and intercept read/write operations.
  4. Manipulate process integrity and availability while hiding the real state.

Other methods: Evil PLC changes PLC configuration/logic through download procedures; connected engineering workstations later initiate upload procedures and can be attacked, disrupting production. RF replay records and resends commands. RF command injection reverse-engineers and alters or creates packets. Malicious re-pairing pairs a hostile transmitter. Malicious reprogramming implants controller firmware for persistent remote access.

Supply-chain types: third-party software compromise, hardware manipulation, service-provider breach, malicious-component injection, and exploitation of trusted relationships.

Real-world use: A plant requires engineering workstations to treat PLC project files as untrusted and verifies controller logic against signed known-good versions.

Tools and commands used here: Shodan, SDR equipment, debuggers, firmware analysis, Metasploit, and modbus-cli.

Countermeasures and defense: Restrict programming modes, authenticate project downloads, separate engineering workstations, validate logic, protect pairing, sign firmware, assess suppliers, and verify received hardware/software.

EXAM FOCUS: Evil PLC targets the workstation through trusted PLC interactions; a PLC rootkit primarily hides and manipulates controller I/O. Trap: choosing replay when the attacker creates new RF packets rather than resending captured ones.

Memory trick: RF methods are "Repeat, Rewrite, Re-pair, Reprogram."

Memory trick: "Nessus Knows known flaws; Fuzzowski Feeds funny frames; Skybox Scores paths."

3.29 ICS hardware analysis, Metasploit, modbus-cli, and DNP3

What it is: Hardware analysis examines chips and their integrated software. Modbus tools discover unit IDs and read/write registers or coils. DNP3 exposure can permit unauthorized remote access when combined with weak configuration.

Analogy: A register is a numbered storage box for a multi-bit value; a coil is a one-bit switch. A unit ID identifies which slave device receives the request.

How it works:

  1. Static/dynamic chip analysis reveals function arguments, missing I/O validation, certificates, key generation, and encryption information.
  2. Metasploit's modbus_findunitid probes unit IDs; correct responses identify active stations. modbusclient selects address, count, host, and unit to read registers.
  3. Install modbus-cli with RubyGems. Read %MW100 or 400101 for registers and %M100 or 101 for coils. Datatypes include word, signed integer, float, dword, and Boolean coil. Save output with --output.
  4. Shodan searches such as TM221ME16R identify specific Schneider PLC models.
  5. For DNP3, discover open services and weak/default access, but validate only with explicit approval because writes can change a process.

Hardware tools: Software: GDB, OpenOCD, Binwalk, Fritzing, Radare2, Ghidra, IDA Pro. Hardware: signal analyzer, multimeter, memory programmer, microcontroller, oscilloscope, soldering tools, microscope, JTAG interface, screwdrivers, tweezers, and converters.

Real-world use: In a testbed, an assessor reads five holding values and demonstrates that network access alone exposes process data, then recommends firewall and monitoring controls rather than changing live values.

Tools and commands used here: Metasploit auxiliary modules, modbus-cli, Shodan, Nmap, Binwalk, GDB, OpenOCD, and hardware instruments.

Countermeasures and defense: Restrict port 502 and DNP3 port 20000 to authorized masters, authenticate remote access externally, log write function codes, segment, and require programming-mode authorization.

EXAM FOCUS: %MW denotes a 16-bit memory word in the shown Schneider syntax; %M denotes a coil. 400101 is a Modbus reference form. Trap: confusing register values with one-bit coils or using UDP for classic Modbus TCP.

Memory trick: "Find the Unit, Set the Host, Read the Register, Mind the Coil."

3.30 OT defenses, Purdue controls, zero trust, and organizations

What it is: OT defense is layered risk management that protects operations without unsafe testing or uncontrolled change.

Analogy: A plant needs gates, visitor logs, trained operators, emergency stops, and rehearsals, not just a taller fence.

Core defenses from the notes: Purpose-built passive sensors; supported technology and tested patches; secure configuration/coding; an asset register; strong changed passwords; VPN-backed layered remote access; perimeter filtering; anti-malware; unused-service hardening; manufacturer patches; IDS and flow measurement; tested third-party web servers; cryptographically signed updates; and periodic audits.

Vulnerability-to-solution pairs: Public exposure needs enterprise firewalls, managed remote access, MFA, and incident response. Remote connections need strong identity, RBAC, and patching. Updates need sandbox testing and hardening. IT/OT connections need segregation, an IDMZ, business-based rules, and secure gateways. Flat OT needs critical/noncritical separation, zones, defense in depth, and zero trust. Wireless needs standard strong encryption. Outbound access needs risk assessment, monitoring, segregation, and a separate update repository. Firewalls need secure configuration and ACLs. IT and OT should use separate username conventions.

Purdue security controls: Levels 4/5 use firewalls, IPS, anti-bot, URL filtering, SSL inspection, antivirus, and DLP. Level 3.5 uses anti-DoS, IPS, anti-bot, application control, and application-layer firewalling. Level 3 adds sandboxing, traffic encryption, monitoring, and USB/port protection. Levels 1/2 use IPS, firewalls, IPsec, security gateways, and authorized RTU/PLC commands. Level 0 adds point-to-point controls, MAC authentication, and additional gateways at Levels 0/1.

Zero-trust sequence: Define the network, map traffic, architect the network, develop the zero-trust policy, then monitor and maintain. Verify users, applications, and devices continuously and grant only required access.

Organizations: OTCC shares best practices among industry and government. OT-ISAC supports operational-technology threat information sharing. NERC develops and enforces electric reliability standards in its jurisdiction.

EXAM FOCUS: Zero trust is not one appliance. It is identity, least privilege, segmentation, and continuous validation. Trap: allowing a vendor permanent broad access because the vendor is trusted.

Memory trick: Zero trust: "Define, Draw, Design, Decide, Detect."

8.3 Pick the BEST option rules

  • If two answers find flaws, choose passive asset/traffic review before active OT scans.
  • If the question asks "which tool", match its unique verb: search, scan, decode, fuzz, emulate, extract, debug, or manage.
  • If a controller is live and safety matters, do not choose fuzzing or write tests.
  • If credentials are default, replace them with unique strong credentials before cosmetic actions such as changing banners.
  • If IT and OT connect directly, choose IDMZ/segmentation rather than only antivirus.
  • If malware persists in firmware, choose trusted reflash and secure boot, not a password reset.
  • If the question describes two fob presses, jamming, and a saved code, choose rolling-code attack over simple replay.
  • If a port is open, do not assume exploitation; validate safely and consider banner ambiguity.
  • If one control solves root cause and another only detects, choose root-cause fixing unless the scenario makes immediate change unsafe.
  • Use commands only on authorized systems; in the exam, operational safety and scope are part of the best answer.

Question 1: IoT architecture

A sensor sends a Zigbee message to a local gateway. The gateway converts it into an IP message. Which IoT architecture layer performs this conversion?

  • A. Edge technology
  • B. Access gateway
  • C. Middleware
  • D. Application

Answer: B. Access gateway. Protocol translation and messaging belong to this layer. A is wrong because edge contains sensors/devices. C is wrong because middleware manages devices/information. D is wrong because applications deliver user functions.

Question 2: Rolling-code scenario

During an authorized vehicle test, the first fob press fails. The test device forwards the first captured code after the second press, unlocks the car, and retains the second code. What is being demonstrated?

  • A. DNS rebinding
  • B. Simple sniffing only
  • C. Rolling-code attack
  • D. Power-analysis attack

Answer: C. Rolling-code attack. Jamming/capture and saving an unused later code are the distinctive sequence. A changes DNS answers. B does not explain forwarding and jamming. D measures chip power rather than RF command codes.

Question 3: Best first OT step

A consultant receives permission to inventory an old water-treatment network. Several PLCs stop if exposed to heavy traffic. What is the BEST first step?

  • A. Fuzz Modbus on every controller
  • B. Run maximum-speed parallel scans
  • C. Review passive traffic and existing asset records
  • D. Write test values to unused coils

Answer: C. Review passive traffic and existing asset records. It builds visibility with minimal process risk. A and B can crash fragile systems. D can change a physical process and is not inventory gathering.

11. Glossary

  • Access gateway: IoT layer that translates protocols and handles messaging.
  • Active scanning: Sending probes to a target to discover services or weaknesses.
  • Actuator: Device that changes a physical process, such as a valve or motor.
  • Asset register: Maintained inventory of systems, owners, versions, and criticality.
  • Backdoor: Unauthorized or hidden method of bypassing normal access controls.
  • BACnet: Building-automation protocol, commonly carried over UDP 47808.
  • Baud rate: Signaling speed configuration for a serial interface such as UART.
  • Binwalk: Tool that identifies and extracts embedded firmware content.
  • BSSID: Identifier of a wireless access-point radio.
  • Botnet: Collection of compromised devices controlled by an attacker.
  • C2: Command-and-control channel used to task compromised systems.
  • CoAP: REST-like application protocol for constrained IoT devices.
  • Coil: One-bit Modbus value that can represent a controllable switch state.
  • Conduit: Controlled communication path between OT security zones.
  • DCS: Distributed control system used to coordinate plant processes.
  • Deepfake: AI-generated or altered media that imitates a real person or event.
  • DMZ: Buffer network separating zones with different trust levels.
  • DNP3: Industrial protocol commonly used by utility SCADA systems.
  • DNS rebinding: Changing DNS answers to make browser script reach another address.
  • Edge layer: IoT devices, sensors, machines, and intelligent edge nodes.
  • EMFI: Electromagnetic fault injection used to disturb chip behavior.
  • EtherNet/IP: Industrial protocol carrying CIP over standard IP networks.
